# English C1 Learning PWA — DeepSeek Coding Brief

> **Status:** Discovery draft. Fill in the decisions in the questionnaire before committing to major architecture choices. Do not silently guess preferences that materially affect the product.

## 1. Project mission

Build a polished, installable Progressive Web App (PWA) that helps one learner progress toward confident, accurate **C1-level English**, with particular emphasis on:

- Advanced grammar and reliable usage
- High-value vocabulary and word families
- Natural collocations
- Idioms and phrasal verbs
- Nuance, register, and choosing the right expression for a situation
- Active recall, repeated practice, and long-term retention
- Applying what is learned in realistic sentences and situations

The app should make learning structured, engaging, and measurable. It should not be merely a static glossary or a generic quiz page.

## 2. Non-negotiable constraints

1. **No AI implementation at runtime.** Do not integrate an LLM, chatbot, AI SDK, AI API, model endpoint, agent, or AI-generated response feature into the PWA. No API key or secret should be required to use it.
2. **No hidden network dependency.** Do not add external APIs, analytics, telemetry, remote databases, or third-party services without explicit approval. Clarify whether all app functions must work offline; do not assume that installability automatically means full offline support.
3. **Content must be deterministic.** Learning explanations, prompts, answers, examples, hints, and feedback should be stored as local/static content or generated by ordinary application logic. Any learning content generated during development must be reviewed and included in the app as data, not generated by an AI at runtime.
4. **Protect learner data.** Do not send study records, answers, or personal information to a server. Ask before adding accounts, cloud sync, analytics, or data sharing.
5. **No fabricated functionality.** Do not present buttons, filters, statistics, or settings that do not work.
6. **No destructive rewrites.** If a codebase already exists, inspect it before changing anything. Preserve working behavior and the current stack unless a change is justified and approved.
7. **Build in verifiable increments.** Make small, coherent changes; run available checks; report what changed and what remains incomplete.

## 3. Product principles

- Teach at approximately C1 level, but adapt practice to the learner's demonstrated performance and identified gaps.
- Favor natural, contemporary English over obscure or literary expressions.
- Teach distinctions in meaning, tone, register, grammar patterns, and typical context—not just translations.
- Use clear examples, including common mistakes and why they are wrong.
- Ensure tasks require active recall and use, not only recognition.
- Provide helpful explanations after answers. Avoid unnecessary text and repetitive explanations.
- Make progress visible without shaming the learner or turning every activity into a competition.
- Keep the interface usable on a phone, tablet, and desktop. TV support is not assumed.
- Keep educational content separate from UI and exercise logic, so it can be expanded and reviewed without rewriting screens.
- Do not use copyrighted course content or scrape a source without permission. Prefer original examples or content with a clear reuse license.

## 4. Intended learning areas

Treat the following as candidate content areas until the learner confirms priorities:

### Grammar
- Advanced tense/aspect choices and time reference
- Articles, determiners, quantifiers, and countability
- Conditionals, mixed conditionals, and hypothetical meaning
- Modal verbs and degrees of certainty, obligation, and criticism
- Passive structures and causative forms
- Relative clauses, participle clauses, and reduced clauses
- Inversion, emphasis, cleft sentences, and fronting
- Subjunctive and formal constructions where useful
- Reported speech and reporting verbs
- Gerunds, infinitives, and verb patterns
- Prepositions and dependent prepositions
- Conjunctions, discourse markers, cohesion, and complex sentence structure
- Punctuation and common advanced-learner errors

### Vocabulary and usage
- High-value C1 vocabulary grouped by theme and communicative function
- Word families, collocations, dependent prepositions, and common patterns
- Phrasal verbs and idioms with register and usage notes
- Synonyms distinguished by nuance, strength, and context
- False friends and common Czech-to-English transfer errors, where relevant
- Formal, neutral, and informal variants
- Business English and everyday English, according to the learner's priorities

### Practice formats to consider
- Spaced-repetition flashcards
- Multiple-choice questions with plausible distractors
- Gap fills and cloze exercises
- Error correction and explanation
- Sentence transformation / paraphrasing
- Word formation
- Collocation matching and completion
- Choose-the-best-expression-in-context tasks
- Sentence building from prompts
- Short writing tasks with deterministic, pre-authored model answers or checklists
- Mixed review sessions that revisit older material

Do not implement every format immediately. Select a focused first release based on the learner's answers.

## 6. Development workflow for DeepSeek

Follow these phases in order unless the user asks for a different sequence.

### Phase 0 — Understand the environment
1. Inspect the repository structure, `package.json`, scripts, framework, existing routes, styling system, tests, and PWA configuration.
2. Identify the actual framework and language before proposing code. Do not assume React, TypeScript, Vite, or any specific library.
3. Run the existing app and checks when possible. Record baseline errors before making changes.
4. Summarize the existing architecture, the likely implementation path, risks, and missing information.
5. Do not replace project configuration or delete files just to make a preferred setup fit.

### Phase 1 — Agree on the minimum viable product
1. Convert the learner's answers into a concise requirements specification.
2. Define the first-release user journey, content model, exercise types, review rules, persistence, and success criteria.
3. Create a small implementation plan with clear milestones.
4. Confirm major irreversible choices (framework migration, storage reset, hosting, sync, licensing, or external services) before doing them.

### Phase 2 — Design the data model
Keep learning content data-driven. Adapt the structure to the existing stack, but consider entities such as:

- `LearningItem`: stable ID, category, level, topic, prompt, accepted answer(s), explanation, examples, tags, and source/license metadata where relevant
- `Exercise`: stable ID, exercise type, referenced learning item(s), task instructions, answer key, distractors when needed, hint, explanation, and scoring rules
- `ReviewState`: item ID, due date, interval/ease or equivalent scheduling values, streak, attempt history summary, and last result
- `StudySession`: date/time, selected mode, items attempted, accuracy, and duration if the learner agrees to tracking it
- `UserSettings`: language of explanations, target variant of English, session length, reminder preferences if supported, and other selected preferences

These are conceptual examples, not mandatory names or a fixed schema. Keep content separate from personal progress. Use stable IDs and define how schema changes are migrated safely.

### Phase 3 — Build one complete vertical slice
Build a small but complete path before expanding the catalog:
1. Open the app.
2. Select or start a practice session.
3. See a clear question or prompt.
4. Submit an answer using the intended interaction.
5. Receive accurate feedback and an explanation.
6. Record the result locally according to the agreed rules.
7. See the next item and a useful end-of-session summary.
8. Reopen the app and verify that progress persists.

Use a small set of carefully checked sample content. Do not mass-produce hundreds of questions before the exercise engine and answer evaluation are validated.

### Phase 4 — Expand and refine
- Add the remaining approved exercise types one at a time.
- Add review scheduling only after the learner flow and persistence work.
- Add progress views after defining exactly what each metric means.
- Add settings and import/export only when included in the requirements.
- Test responsive behavior and installation on the target devices.

### Phase 5 — Release readiness
- Run all available lint, type-check, unit, integration, and production-build scripts.
- Verify installation and manifest metadata.
- If offline capability is required, test a cold launch and core study flows with the network disabled; verify cached routes and assets, as well as data persistence.
- Test keyboard use, focus states, readable contrast, empty states, errors, and small screens.
- Verify that no AI SDK, AI API, external content API, or unapproved telemetry has been introduced.
- Summarize what was tested, test results, known limitations, and exact run/build commands.

## 7. Coding standards

- Follow the established project's conventions and existing framework.
- Prefer readable, maintainable code over clever abstractions.
- Use TypeScript and strict typing if the project already uses TypeScript or the user approves adopting it.
- Keep UI components reasonably small; separate learning content, domain logic, persistence, and presentation.
- Avoid giant components, duplicated question data, magic values, and hidden side effects.
- Validate user input and guard against malformed or missing stored data.
- Handle first launch, empty content, interrupted sessions, storage failure, and content-version changes gracefully.
- Use stable keys and IDs; never use array indexes as permanent learning-item identifiers.
- Avoid dependencies for functionality that can be implemented safely with the existing stack. Explain any new dependency and its purpose.
- Do not claim that code has run or passed tests unless it actually has.
- Do not silently suppress errors, delete tests, or weaken checks to get a passing build.
- Do not put API keys, secrets, or personal data in source code.

## 8. PWA and local-data requirements

Confirm the intended offline and data behavior with the learner. At minimum, investigate and document:

- Whether the app should be installable on iOS, Android, Windows, and/or other platforms
- Whether all core lessons must work offline after installation or first load
- Service worker and caching strategy appropriate to the selected framework
- Local persistence choice based on data complexity (for example, IndexedDB for structured progress, or a simpler store for small settings)
- What happens if site data is cleared or the app is reinstalled
- Whether progress export/import is required for backup or device migration
- How app updates preserve existing study history
- Whether notifications or reminders are needed and are technically appropriate for target platforms

Do not add a backend, account system, cloud sync, or external API unless explicitly requested. If offline operation is required, bundle the approved learning content with the app and ensure that essential app behavior does not depend on remote fonts, scripts, images, or services.

## 9. Educational-content quality rules

Every learning item must be accurate, natural, and suitable for the intended level and target English variety.

Where appropriate, include:
- A concise definition or rule
- A natural example in context
- A common error or contrast with a nearby expression
- Typical collocations or grammatical patterns
- Register/region notes where meaningful
- A short explanation of why the answer is correct
- More than one accepted answer when English usage genuinely permits it

For answer evaluation:
- Do not rely on brittle exact-string comparison when punctuation, capitalization, contractions, or legitimate alternatives should be accepted.
- Normalize answers only where it is safe and pedagogically appropriate.
- Distinguish a genuinely wrong answer from an alternative valid answer.
- When an exercise has ambiguous answers, rewrite the task or explicitly list valid alternatives.
- Do not label informal language as universally wrong when it is appropriate in informal contexts.
- Prefer concise, high-quality content over large amounts of questionable content.

## 10. Progress and review design

Do not choose a spaced-repetition algorithm or scoring system silently. First establish:
- What counts as “known,” “due,” “incorrect,” and “mastered”
- How confidence ratings, hints, and response time should affect scheduling, if at all
- Whether the learner wants daily goals, streaks, reminders, or gamification
- Whether progress should be tracked by topic, item, skill, or a combination

Show accurate and interpretable metrics. Do not manufacture a proficiency level or claim CEFR certification from quiz scores. Label any in-app estimate as an informal practice indicator, not an official CEFR assessment.

## 11. UX and accessibility

- Use clear, consistent navigation and obvious actions.
- Keep the central study interaction fast and uncluttered.
- Make it easy to review an explanation without losing session progress.
- Support keyboard navigation, visible focus, meaningful labels, and screen-reader-friendly controls.
- Provide clear loading, empty, success, and error states.
- Avoid punitive streak mechanics or distracting gamification unless requested.
- Confirm the desired visual style and language before investing in a detailed design system.

## 12. Definition of done for every milestone

A milestone is complete only when:
- Its behavior matches the agreed requirements.
- The main success path and at least the most important failure/edge cases have been checked.
- Existing functionality has not regressed, to the extent verified by tests.
- Content and answers are checked for correctness.
- Persistence behaves as specified.
- There are no dead controls or unexplained placeholders in the delivered scope.
- Relevant automated checks and the production build have been run, or any inability to run them is clearly disclosed.
- The handoff report names changed files, key decisions, tests run and results, remaining issues, and the next recommended step.

## 13. Learner questionnaire

Answer what you can. “Not sure—recommend an option” is a valid answer. The coding agent should ask these in a few logical batches and avoid asking again after an answer is recorded.

### A. Learning goals and target English
1. Is your main goal confident spoken English, writing, business communication, general fluency, exams, or a combination? Rank your top three.
2. Should the app focus on American English, British English, or explain differences when relevant?
3. Which situations matter most: meetings, negotiations, presentations, emails, small talk, travel, media, everyday conversation, or something else?
4. Do you want the content strictly at C1, or a system that identifies gaps below C1 and revisits them when needed?
5. Should examples be tailored to your work and interests, or remain broadly general-purpose?
6. Which areas currently feel weakest: grammar accuracy, vocabulary range, collocations, idioms, phrasal verbs, listening, pronunciation, spontaneous speaking, writing, or nuance/register?

### B. Language and explanations
7. Should explanations be in English only, Czech only, or primarily English with optional Czech clarification?
8. How detailed should explanations be: brief rule and example, medium explanation with common mistakes, or deep explanation with contrasts and exceptions?
9. Should the app show phonetic transcription, audio/pronunciation guidance, stress marks, or none of these? Remember that audio files or browser speech synthesis may have platform limitations.
10. Should it explicitly explain Czech-to-English interference and false friends?
11. Should it teach slang and informal expressions, or prioritize neutral and professional language?

### C. Study routine and lesson structure
12. How much time do you realistically want to study per day, and on how many days per week?
13. What should the default session length be: 5, 10, 15, 20, or a custom number of minutes?
14. Should the app automatically choose the next activity, let you choose a topic, or offer both modes?
15. Do you prefer a structured course/path, a daily personalized queue, a searchable library, or a combination?
16. Should each session mix grammar, vocabulary, collocations, and idioms, or focus on one area at a time?
17. Should a session start with new material, review due items, or balance new and review content?

### D. Exercise types and feedback
18. Which exercise formats do you most want in the first release? Pick up to five from: flashcards, multiple choice, gap fills, error correction, sentence transformation, word formation, collocation practice, phrasal verbs/idioms in context, sentence building, short writing, translation, or mixed review.
19. Should Czech-to-English translation be included, or should practice happen mostly in English?
20. For typed answers, should the app check only pre-authored accepted answers, or should the first release avoid typed responses and use selection-based tasks? No AI will judge free-form answers at runtime.
21. Should an answer reveal the explanation immediately, after you request a hint, or only after your attempt?
22. Do you want a retry option, hints, confidence rating (e.g., “easy / hard”), or a “mark for later” action?

### E. Content volume and review
23. Should the app start with a small, carefully reviewed foundation (for example 100–200 items) or a much larger content library? How much content would feel substantial to you?
24. Should content be organized by grammar topic, CEFR skill, theme, frequency/usefulness, real-life situation, or all of these?
25. Do you want spaced repetition? If yes, should the app recommend a simple proven approach, or do you have an existing system in mind?
26. Should the app keep an error notebook and automatically bring recurring mistakes back into practice?
27. Do you need content sources or references visible, or is reviewed original content sufficient?

### F. Progress, motivation, and privacy
28. What progress information matters: accuracy, retention, time studied, items learned, topic mastery, weak areas, streaks, or a weekly review?
29. Do you want badges, points, levels, daily goals, streaks, or a deliberately calm/no-gamification experience?
30. Should all data stay on the device? Do you need export/import so you can back up progress or move to another device?
31. Do you want reminders or notifications? If yes, on which devices and at what time?

### G. Platform, implementation, and release
32. What devices must it support first: iPhone, Android, Windows desktop, tablet, or several?
33. Where should it be hosted, if anywhere? Do you already have a domain or hosting provider, or should the app be usable locally without a public deployment?
34. Must all lessons work offline after installation, including a first launch with no connection, or is internet needed only for initial loading/updates acceptable?
35. Is there an existing code repository? If so, what framework/language is it using, and can DeepSeek inspect the project before coding?
36. Do you have a preferred stack (for example, React + TypeScript + Vite), or should the coding agent recommend the simplest maintainable option based on the existing project?
37. Do you want automated tests, and are there tools already configured in the repository?
38. What visual style do you prefer: minimalist, editorial/textbook, modern app with cards, playful/gamified, or another reference?
39. What would make version 1 a success for you after two weeks of use? Name the three most important outcomes.
40. Are there any apps, websites, or learning experiences you like or dislike, and what specifically should be copied or avoided (without copying protected design/content)?

## 15. Required response format after each coding task

At the end of each implementation step, report:

1. **Implemented:** concrete user-visible behavior added or changed.
2. **Files changed:** file paths and their purpose.
3. **Validation:** exact commands run and their results. Never claim a check passed if it was not run.
4. **Known issues:** limitations, unimplemented pieces, and risks.
5. **Decisions needed:** only questions that block the next meaningful step; do not repeat answered questions.
6. **Next step:** one small, logically sequenced implementation task.

**Primary rule:** correctness, maintainability, and the learner's actual needs take precedence over generating a large quantity of code quickly.
